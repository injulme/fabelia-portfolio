파벨리아 (Fabelia)

원고·인물·장소·플롯·관계도를 한 화면에 펼쳐 두고 쓰는, 소설가를 위한 집필 도구

Next.js 웹앱 하나를 기획·프론트엔드·백엔드·결제·배포까지 혼자 만들고 운영하고 있습니다. 9개월 동안 데이터 저장소를 IndexedDB → 로컬 폴더 → 서버(Supabase)로 세 차례 옮기면서도 화면 쪽 호출부를 거의 고치지 않도록 경로 기반 저장소 경계를 설계했고, 그 위에서 충돌 감지·복구 초안·원고 암호화·정기결제·AI 기능을 쌓았습니다.

Overview

무엇을, 무엇으로 만들었나

작가는 한 작품 안에서 원고와 설정 자료(인물·장소·위키), 플롯보드, 관계도를 계속 오갑니다. Fabelia는 이것을 파일 단위 JSON으로 다루고, 사이드바 파일 트리와 dockview 분할 패널 위에서 여러 문서를 동시에 띄워 편집하게 합니다.

영역 기술 내용
Framework Next.js 16 (App Router), React 19, TypeScript 집필 화면 · 서재 · 관리자 콘솔을 한 앱에서 제공
Editor · Layout Tiptap 3 (ProseMirror), dockview, React Flow 리치텍스트 원고 · VSCode형 분할 패널 · 관계도 다이어그램
State · Form Zustand, react-hook-form + zod 설정·레일 상태(persist) · 모든 입력 폼의 검증
Backend Next.js Route Handler (Node.js 런타임), Supabase (Postgres RPC · Storage · RLS), Auth.js REST API(/v1/*)와 AI·결제·크론 API, 작품·파일 행, 이미지 버킷, 구글 로그인 쿠키 세션
결제 · AI 나이스페이먼츠 빌링, OpenAI (Responses · Images API) 4등급 정기 구독 · 맞춤법/에이전트/원고 초안/이미지 생성
Infra Vercel Pro (icn1), Vercel Firewall, Resend 배포 · 분당 요청 상한 · 피드백·계정 안내 메일
Shell Electron, Capacitor 운영 웹을 그대로 띄우는 데스크톱·모바일 껍데기

이슈 타임라인

2026.022026.11
    ISSUE 01 · 2026.04 – 2026.10

    저장소 세 번의 전환과 서버 이관 결정

    IndexedDB → 로컬 폴더 단독 → 서버. 저장 기술보다 「사용자가 원하는 것이 무엇인가」에 집중하기로 했습니다. 경로 기반으로 구성한 덕분에 화면 쪽 호출부는 유지한 채 저장소만 갈아끼우는 방식으로 쉽게 이관할 수 있었습니다.

    아키텍처SupabaseFile System Access API

    배경

    「작가가 자기 원고 파일을 직접 갖는다」는 방향으로 로컬 폴더(File System Access API)를 1차 저장소로 삼았습니다. 폴더 트리 + 분할 패널 화면과 파일 단위 저장이 같은 시제품에서 함께 나온 결정이었습니다.

    문제

    • Chromium·Electron에서만 동작 — Safari·Firefox·iOS에는 폴더 API가 없어 모바일 확장이 막혀 있었습니다.
    • 브라우저를 다시 켤 때마다 「권한 다시 주기」 클릭, 첫 실행의 폴더 피커를 없앨 수 없었습니다.
    • 크롬에 디렉터리 move()가 없어 폴더 이름변경이 재귀 복사 후 삭제였습니다 — 수 초간 화면을 잠그고, 중간에 실패하면 반쪽 상태가 남았습니다.
    • 여러 파일을 원자적으로 쓸 수 없고, 파인더에서 고친 파일 때문에 색인을 둘 수 없어 검색이 매번 전체를 훑었습니다.

    선택지와 결정

    선택지이점단점
    로컬 폴더 유지오프라인 · 파일 소유 · 운영비 0브라우저 제약 · 권한 · 원자성 없음 · 여러 기기 불가
    IndexedDB 단독모든 브라우저 · 원자성 · 색인브라우저 축출로 데이터 소실 위험 · 여러 기기 불가
    IndexedDB + 드라이브 백업소실 위험 대부분 상쇄백업은 동기화가 아님 — 두 기기가 각자 고치면 한쪽이 덮어써짐
    서버(Supabase)모든 환경 · 트랜잭션 · 서버 색인 · 여러 기기로그인 필수 · 오프라인 불가 · 운영비 · 원고 보관자 책임

    이유: 타 제품 분석 과정에서 사용자들이 모바일을 적극적으로 활용한다는 사실을 알았습니다. 제품을 여러 기기에서 사용할 수 있는 방안을 고안했으나, 드라이브 위에서 동기화 엔진을 만드는 것은 트랜잭션도 서버 병합도 없는 환경에서 사용자에게 좋은 경험을 남기기 어렵다고 판단했습니다. 사용자가 아직 없던 시점이라 데이터 이관 없이 옮길 수 있는 마지막 기회이기도 했습니다.

    구현

    • 경계를 미리 경로로 옮겨 둔 것이 핵심이었습니다. 저장소 인터페이스(IWorkspaceStorage)의 인자를 폴더 핸들에서 직렬화 가능한 경로(NodeRef)로 바꿨고, 모든 호출은 첫 인자로 저장 영역('workspace' | 'app')을 명시하게 했습니다. 서버에서는 이 영역이 그대로 work_entry.area 칼럼이 됩니다.
    • 서버가 로컬 폴더와 같은 의미론(폴더 · 이름변경 · 이미지 사이드카 동반 이동 · 같은 이름 거절)을 Postgres RPC로 구현해, 화면 쪽은 저장소가 바뀐 사실을 모르게 했습니다.
    • 이미지 키는 경로 대신 uuid로 두어 이름변경과 무관하게 했습니다.
    • 이관은 8단계로 나눠 1~7단계를 이틀, 문서·검증 전환·처리방침 반영까지 6일 만에 마쳤습니다.

    결과

    • 경로 기반 설계 덕분에 저장소를 쓰는 46개 파일의 호출부가 바뀌지 않았습니다.
    • 모든 브라우저(모바일 포함)에서 동작하게 되어, 현재 Capacitor 모바일 앱의 전제가 됐습니다.
    • 폴더 이름변경이 「재귀 복사 + 삭제」에서 트랜잭션 한 번이 됐고, 서버 검색 색인을 둘 수 있게 됐습니다.

    잘한 점

    ISSUE 02 · 2026.10.25 – 10.26

    원고 암호화와 무중단 운영 이관

    서버로 옮기면서 「남의 저작물 보관자」가 됐습니다. 사용자에게 약속할 수 있는 것과 없는 것을 먼저 나누고, 그 범위 안에서 봉투 암호화를 적용했습니다.

    AES-256-GCMEnvelope Encryption보안

    문제

    원고가 jsonb·text 평문으로 저장돼, Supabase 대시보드나 SQL 편집기로 행을 열면 그대로 보였습니다. 서버 키 하나, DB 덤프 하나가 새면 원고 전체가 샙니다. 「운영자가 확인차 열어 보지 않는다」는 정책으로만 막고 있었습니다.

    선택지와 결정

    방식장점기각·채택 이유
    종단간 암호화(B)운영자도 볼 수 없음구글 로그인뿐이라 키를 유도할 비밀이 없음 · 키를 잃으면 복구 불가 · 서버 검색 상실 · AI 기능 때문에 어차피 완전한 약속 불가
    서버 측 봉투 암호화(A)DB·백업·키 유출에 대응 · 검색·AI 유지위협 모델(대시보드 열람 · 키 유출 · 덤프 유출 · 우발적 열람)을 모두 막고, 클라이언트 계약을 바꾸지 않음

    구현

    • 원고·검색 평문·버전 스냅샷을 Route Handler가 AES-256-GCM으로 암호화해 바이너리 칼럼(bytea)에 넣습니다. 키는 작품마다 하나(DEK)이고, DEK는 환경변수의 마스터 키(KEK)로 감싸 work 행에 둡니다.
    • AAD(추가 인증 데이터)로 암호문을 작품·행에 묶어, 남의 행에 붙여 넣은 암호문은 복호화 자체가 실패합니다.
    • KEK는 id가 붙은 묶음({"k1": ...})으로 두어 교체 경로를 열어 두었고, 개발과 운영은 다른 키를 씁니다.
    • 암호화 계층은 왕복·변조 탐지·AAD 불일치·DEK 감싸기·KEK 판독을 키·DB 없이 1초 안에 확인하는 검증 스크립트를 만들었습니다.
    • 서버 검색은 라우트가 복호화한 뒤 대조하도록 옮겼습니다. 큰 원고(약 3.9MB) 왕복이 실패해 압축을 넣은 뒤 통과시켰습니다.
    • 운영 이관은 마이그레이션을 두 단계로 나눴습니다. 먼저 평문 칼럼을 남긴 채 암호문 칼럼만 추가하고, 새 코드를 배포한 뒤 이관 스크립트로 기존 원고를 암호화해 옮겼습니다. 스크립트는 암호문을 쓰기 전에 메모리에서 다시 풀어 원본과 대조하고, 하나라도 다르면 그 자리에서 멈춥니다. 동작 확인이 끝난 뒤에야 두 번째 마이그레이션으로 평문 칼럼을 지우고 NOT NULL 제약을 걸었습니다.

    결과

    • 운영 DB의 기존 원고 60건 · 버전 스냅샷 83건을 암호화해 이관했습니다.
    • 약 3.9MB 원고의 저장 요청이 DB 제한 시간(8초)에 걸려 실패하던 것을, 암호화 전에 압축해 0.2~0.6초로 줄였습니다.

    회고

    잘한 점

    모든 데이터를 암호화하기보다, 사용자에게 민감한 원고 본문·검색 평문·버전 스냅샷을 중심으로 암호화했습니다. 작품명·파일 이름·이미지는 범위에서 뺐고, 백업과 AI 사용에 대해 사용자에게 약속할 수 있는 범위를 기준으로 정했습니다.

    아쉬운 점

    큰 원고(약 3.9MB) 저장이 실패한 뒤에야 압축을 넣은 점이 아쉽습니다. 평문일 때는 DB가 압축해 주던 데이터가 암호문이 되면서 압축되지 않았고, 요청이 DB 제한 시간을 넘겼습니다. 암호화로 늘어나는 크기는 설계 단계에서 먼저 따졌어야 했습니다.

    배운 점

    KEK를 잃으면 원고 전부를 잃는 구조라, 오프라인 사본 절차까지 운영 문서에 넣었습니다. 암호화는 기능 구현만큼 키를 지키는 운영 절차가 중요하다는 것을 배우는 계기가 되었습니다.

    다음에는

    사용자가 민감하게 여기는 기능은 기획 단계에서 미리 고려한 뒤에 구현하려 합니다.

    AI 기능 설계 — 원가, 동시성, 그리고 방향 전환

    맞춤법 · 에이전트 대화 · 원고 초안 · 다이어그램 · 이미지 생성. 기능을 늘리는 것보다 「한도가 실제로 지켜지는가」와 「작가에게 필요한 방향인가」를 더 오래 고민했습니다.

    OpenAI Responses APINDJSON 스트림사용량 과금

    AI 모델 통합

    텍스트는 OpenAI, 이미지는 Gemini로 나뉘어 있던 것을 OpenAI 하나로 모았습니다. 맞춤법 모델은 A/B 테스트를 4회 진행하여 과교정 0 · 잘못 적용 0을 확인한 뒤 확정했습니다. 플랜별 사용량 상한은 「1인당 최대 원가」가 순매출을 넘지 않도록 역산했습니다.

    동시 요청이 한도를 뚫는 문제

    문제: AI 기능은 플랜마다 월 사용량 상한이 있습니다. 처음에는 「남은 양 확인 → AI 생성 → 사용량 더하기」 순서로 처리했는데, 확인과 더하기 사이에 AI 생성 시간이 끼어 있어 그사이 들어온 요청도 같은 남은 양을 보고 통과했습니다. 예를 들어 이미지가 1장 남은 상태에서 지도와 캐릭터 이미지를 동시에 만들면 둘 다 생성됐습니다. 또 사용량 조회가 실패하면 「사용량 0」으로 읽어서, DB 장애 동안에는 한도가 사실상 풀려 있었습니다.

    구현: 공연 좌석을 먼저 잡아 두고 결제하는 것처럼, AI를 호출하기 전에 사용량을 먼저 예약하도록 바꿨습니다.

    • 예약: 지금 사용량이 상한 미만이면 예약량을 더하고 통과하도록 처리합니다. 확인과 더하기가 한 번에 일어나므로, 동시에 온 두 번째 요청은 첫 번째가 더한 뒤의 값으로 판정받습니다. 예약량은 맞춤법이면 보낼 글자 수, 이미지면 1장, 텍스트 AI면 입력 글자 수에 최대 출력 분량을 더한 값입니다.
    • 정산: 생성이 끝나면 「실제 사용량 − 예약량」만큼 보정합니다. 실패하거나 빈 응답이면 예약 전체를 돌려줘, 성공한 만큼만 사용량으로 셉니다. 스트리밍 응답은 스트림이 끝나는 시점에 정산해 예약이 남지 않게 했습니다.
    • 장애 시 차단: 사용량 표를 읽지 못하면 통과시키지 않고 막습니다. 사용량을 알 수 없을 때는 원가가 새는 것보다 잠시 막히는 편이 낫다고 판단했습니다.

    AI가 플롯을 짜는 기능을 접은 이유

    줄거리를 넣으면 AI가 플롯 카드를 만들어 컬럼에 배치하는 기능을 먼저 만들었습니다. 그런데 실제 작가의 작업 순서는 플롯을 먼저 짜고, 그 플롯을 따라 원고를 쓰는 것이 일반적입니다. AI가 플롯을 짜려면 결국 이야기 전체를 알고 이해하고 있어야 하는데, 그 이해는 작가에게 있습니다. AI가 플롯을 짜는 기능은 작가의 작업 흐름과 반대 방향으로 흘러가고 있었습니다.

    72회 생성 실험을 진행한 결과, 컬럼 이름을 「1부~4부」로 바꾸고 설명을 빼면 배치 일치율이 59%로 떨어져, 모델은 줄거리를 이해하기보다 기계적으로 나누고 있었습니다.

    결정: AI 플롯 카드 생성을 걷어내고 작가가 플롯을 짜면 그 플롯으로 AI가 원고 초안을 쓰는 방향으로 변경했습니다.

    이유: 이야기의 뼈대인 플롯은 작가의 몫이고, AI는 그 뼈대를 문장으로 옮기는 쪽이 작가의 작업 순서와 맞는 역할이라고 판단했습니다.

    결과

    • 텍스트·이미지 AI를 OpenAI 하나로 모아, API 키와 과금 경로를 하나로 줄였습니다.
    • 동시 요청이 한도를 넘을 수 있는 양을 요청 하나의 예약량으로 줄였고, DB 장애 중에도 한도가 열리지 않습니다.
    • AI 플롯 카드 생성을 걷어내고, 작가가 짠 플롯 카드로 AI가 원고 초안을 쓰는 기능을 출시했습니다.

    회고

    잘한 점

    AI 기능을 붙일 때마다 「사용자 한 명이 끝까지 쓰면 원가가 얼마인가」부터 계산했습니다. 기능보다 원가와 한도를 먼저 정해 두어, 기능이 늘어나도 요금제가 안정적으로 유지되도록 설계했습니다.

    아쉬운 점

    AI 응답은 느리고 언제든 실패할 수 있다는 점을 처음부터 설계에 넣지 못했습니다. 생성 중에 들어온 요청, 도중에 끊긴 스트리밍, DB 장애 같은 경우를 하나씩 겪은 뒤에야 예약과 정산 구조로 정리했습니다.

    배운 점

    AI의 결과가 그럴듯해 보인다고 해서 제대로 이해한 것은 아니라는 점을 배웠습니다. 같은 입력에도 결과가 달라지고, 조건을 바꿔 실험해 봐야 실제로 이해하고 있는지 알 수 있었습니다.

    다음에는

    AI 기능을 기획할 때 「AI가 할 수 있는가」보다 「작가가 이 일을 AI에게 맡기고 싶어 하는가」를 먼저 묻고, 작은 실험으로 확인한 뒤에 구현하려 합니다.

    웹 하나, 껍데기 셋 — Electron과 Capacitor

    「기능은 웹이 단일 소스」라는 원칙으로 데스크톱·모바일 앱을 운영 웹을 띄우는 얇은 껍데기로 설계했습니다.

    배경

    저장소를 서버로 옮긴 이유(이슈 01)는 「여러 기기에서 쓸 수 있어야 한다」는 것이었습니다. 타 제품을 분석하면서 사용자들이 모바일을 적극적으로 활용한다는 사실을 알았고, 서버 이관으로 모든 브라우저에서 동작하게 되면서 앱으로 넓힐 전제가 갖춰졌습니다.

    기획 단계의 요구는 두 가지였습니다. 데스크톱 앱은 웹과 기능이 거의 같아야 하고, 모바일 앱은 가능하면 같게 하되 비용이 너무 크면 모바일 전용 화면도 검토한다는 것이었습니다. 플랫폼마다 기능을 따로 만들면 같은 기능을 여러 번 고쳐야 하므로, 기능은 웹 하나에 두고 앱은 그 웹을 띄우는 껍데기로 만드는 방향을 잡았습니다.

    설계

    항목구조
    화면운영 URL을 그대로 로드
    인증시스템 브라우저 로그인 → fabelia:// 딥링크 일회용 코드 → 웹과 같은 쿠키 세션
    갱신웹 배포가 즉시 반영 · 껍데기는 드물게

    구현

    • 데스크톱 로그인: 일회용 코드는 암호화 토큰(JWE)에 담고, 코드를 가로채도 쓸 수 없도록 PKCE로 묶었습니다. 또 앱 창 안에서 구글 로그인을 직접 부르면 막히므로 로그인 시작점을 startGoogleSignIn 하나로 모았습니다.
    • 종료 시 저장: 앱을 닫기 전에 대기 중인 자동저장을 마무리하는 등록 지점을 두었습니다.
    • 모바일 앱: Capacitor 앱은 데스크톱과 같은 로그인 경로를 재사용합니다. 데스크톱은 여러 패널을 나란히 띄우는 화면(dockview)이지만, 모바일에서는 한 번에 한 화면만 보이도록 배치를 새로 만들었습니다. 「앱에서 실행 중인가」와 「모바일 크기 화면인가」는 따로 판단하게 해, 모바일 브라우저로 접속해도 같은 모바일 배치가 나옵니다. 또 모바일에서는 패널 라이브러리(dockview)를 내려받지 않도록, 그 라이브러리를 쓸 수 있는 파일을 정해 두고 검사합니다.

    결과

    • 하나의 운영 웹으로 macOS 앱을 빌드해 서명·공증 후 배포했고, 자동 업데이트로 새 버전을 받아 다시 켜지는 것까지 확인했습니다.
    • 같은 웹으로 iOS 앱을 빌드해, 시뮬레이터에서 구글 로그인부터 원고 저장까지 정상 동작을 확인했습니다.

    회고

    잘한 점

    기능의 원본을 웹 하나로 두고 데스크톱·모바일은 운영 URL을 띄우는 껍데기로 만들어, 웹 배포만으로 모든 플랫폼에 기능이 반영되도록 설계했습니다.

    아쉬운 점

    모바일을 고려하지 않은 초기 구조에서 출발하다 보니 화면 배치를 미리 분리해 두지 않았고, 모바일을 지원하는 과정에서 기능 검증을 여러 번 반복해야 했습니다.

    배운 점

    앱 껍데기만 분리하면 하나의 웹으로 여러 플랫폼을 운영할 수 있다는 것을 배웠습니다.

    다음에는

    웹을 앱 껍데기로 감싸 만든 첫 프로젝트라, 앱 사용 경험에 대한 이해는 아직 부족합니다. 출시 후 사용자 피드백을 받아 모바일 경험을 개선해 나가려 합니다.

    ISSUE 06 · 2026.02 – 진행 중

    AI와 함께 개발하기 위한 문서 체계

    Claude Code를 페어 프로그래머로 쓰면서, 「같은 함정을 두 번 밟지 않게」 하는 것이 코드만큼 중요했습니다.

    Claude Code문서 주도 개발

    문제

    규약과 함정을 한 파일(CLAUDE.md)에 쌓다 보니 18만 자를 넘었고, 끝난 작업 기록과 지금의 규칙이 섞여 무엇이 유효한지 알기 어려워졌습니다. 「아직 확인하지 않았다」는 메모가 곳곳에 흩어져 끝났는지 아무도 몰랐습니다.

    결정과 구현

    • 문서의 역할을 넷으로 나눴습니다 — 전역 규약(CLAUDE.md) · 미룬 작업(TODO.md, 끝나면 줄째 삭제) · 기억할 과거(HISTORY.md, 동작 근거로 쓰지 않음) · 영역별 규약(.claude/rules/*.md 22개,해당 파일을 열 때만 로드).
    • 큰 작업은 계획 문서(결정 표 · 위협 모델 · 런북)를 먼저 쓰고 승인한 뒤 착수합니다. docs/에 40여 개의 계획·결정 문서가 있습니다.
    • 걷어낸 기능도 「무엇이 있었고, 왜 걷어냈고, 다시 만들 때 어떤 함정이 있는가」를 남깁니다.

    회고

    잘한 점

    걷어낸 기능까지 「왜 걷어냈고, 다시 만들 때 무엇이 함정인가」를 남겨, 지난 결정의 기록이 다음 설계의 입력이 됐습니다.

    아쉬운 점

    규약을 한 파일에 쌓아 CLAUDE.md가 18만 자를 넘을 때까지 정리를 미뤘습니다. 끝난 기록과 지금의 규칙이 섞여 무엇이 유효한지 흐려졌습니다.

    배운 점

    문서가 긴 것보다, 지금 유효한 규칙과 지난 기록이 섞이는 것이 더 나쁜 결과를 가져올 수 있다는 것을 배웠습니다.

    다음에는

    「미룬 작업은 끝나면 지우고, 기록은 따로 둔다」는 역할 분리를 처음부터 문서 구조에 담으려 합니다.

    Retrospective

    이 프로젝트에서 얻은 것

    파벨리아(Fabelia) 프로젝트를 진행하면서 가장 많이 한 일은 기능을 만드는 것만큼, 만든 것을 근거를 갖고 걷어내는 일이었습니다.

    1. 01

      기획 역량

      사용자의 니즈에서 제품 방향을 정한다

      저장 기술보다 사용자가 제품을 어떻게 쓰는지를 먼저 봤습니다. 타 제품 분석에서 사용자들이 모바일을 적극적으로 활용한다는 것을 확인하고 저장소를 서버로 옮겨 여러 기기에서 쓸 수 있게 했습니다. AI 플롯 생성은 작가의 작업 순서(플롯 → 원고)와 반대라는 판단과 72회 실험 결과를 근거로 걷어내고, 작가가 짠 플롯으로 원고 초안을 쓰는 기능으로 방향을 바꿨습니다.

    2. 02

      디자인(UX) 역량

      사용자가 머무는 곳과 망설이는 곳을 데이터로 본다

      홈페이지를 만들 때 Microsoft Clarity로 사용자의 클릭·스크롤 패턴을 살펴, 사용자가 어디에 오래 머물고 어디서 망설이는지 확인했습니다. 앱에서는 여러 패널을 나란히 띄우는 데스크톱 화면이 모바일에는 맞지 않는다고 보고, 한 번에 한 화면씩 넘기는 모바일 배치를 따로 만들었습니다.

    3. 03

      기술 역량

      필요한 기능에 맞는 기술을 고른다

      기능이 요구하는 조건을 먼저 정하고 기술을 골랐습니다. 여러 기기 사용이 필요해지자 IndexedDB·로컬 폴더 대신 트랜잭션과 서버 색인이 있는 Supabase로 옮겼고, 원고 암호화는 검색과 AI 기능을 지키기 위해 종단간 암호화 대신 서버 측 봉투 암호화를 택했습니다. 데스크톱·모바일 앱은 기능을 웹 하나에 두기 위해 운영 웹을 띄우는 Electron·Capacitor 껍데기로 만들었습니다.

    4. 04

      문제 해결 역량

      원인을 끝까지 쫓아 재발을 막는다

      에러 없이 조용히 틀리는 문제를 끝까지 추적했습니다. 한글 IME 조합 중 Enter의 중복 입력은 규약과 자동 검증으로, 동시 요청이 사용량 한도를 넘는 문제는 「예약 → 생성 → 정산」 구조로, 큰 원고의 저장 실패는 암호화 전 압축으로 해결했습니다. 해결에서 끝내지 않고 같은 실수가 다시 나지 않도록 규칙으로 남겼습니다.

    5. 05

      AI 협업·운영 역량

      AI를 동료로 두고 개발부터 운영까지 혼자 책임진다

      AI를 페어 프로그래머로 두고, 지금 유효한 규칙·결정·지난 기록을 역할별 문서로 나눠 함께 일했습니다. 이 체계 덕분에 1인 개발로도 운영 DB 이관, 정기 결제, 데스크톱·모바일 배포까지 맡을 수 있었습니다. 운영 DB 이관은 런북을 먼저 쓰고 실행했고, 실사용자가 생긴 뒤에는 마이그레이션을 하위 호환 · 한 트랜잭션 · 승인 후 운영 적용으로 관리했습니다.
